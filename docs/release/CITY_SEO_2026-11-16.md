**What competitors answer** (two pages read: gelatogo.net, wanderlustcreamery.com): packages and cart sizes, guest minimums, pricing structure, lead time, branding, flavors, service area. **Gap we fill:** the organizer's side of planning (serving space, venue rules and arrival windows, timing around a reception or work schedule, shade for outdoor events, choosing between treats, shared ZIP codes needing the venue city). We cannot answer price, minimums or lead time (no approved facts; no public minimums), so those are not on city pages.

**City vs. other pages:** treat details stay on treat pages and occasion details on event pages; city pages carry local planning and coverage, linking to both through the existing treat cards, occasion cards, nearby cities and breadcrumbs.

**Limitations (stated plainly):** no competitor copy was reused or paraphrased. Official local sources were **not** used to verify per-city facts, so no local facts are claimed (no venues, landmarks, demographics, travel times, prices, availability or customers). Evidence per city comes only from the location database: county, number of served ZIP codes, cities sharing its ZIP codes, nearby cities, and a short list of places with special logistics.

## 3. Content

Stored only in the existing city fields (ACF Free, `cic_city_editorial` records via `CityStore::ensure_editorial`, the same path as the admin button). No template or design change; images stay inherited from the Service Areas template.

- **185 generated cities:** a main planning angle (home party, booked venue, reception schedule, workplace, school, comparing treats, outdoor timing, larger guest list, mixed ages, first-time organizer) plus a secondary angle, a treat emphasis and an occasion emphasis that follows the angle. Distinct H1, subtitle, intro (with the service and freezer-equipment explanation and a treat reason), plans text, call panel, occasions heading, coverage note and check text, 4 FAQs, closing quote heading/note, search title (≤ 62 characters with the site name) and description (≤ 160).
- **Coverage accuracy:** cities with shared ZIP codes name the sharing cities and explain choosing the venue city (the existing coverage rule); larger cities say service is confirmed per ZIP code; no ZIP lists are hard-coded.
- **16 written cities and Los Angeles:** content kept unchanged; published and marked Reviewed.
- **Similarity review** (sentence sets, city name normalized): every H1, intro, title and description unique; 185 distinct FAQ sets; median page overlap 3.7%; no pair above 0.5 (2 pairs at 0.40–0.42, inspected: the shared part is the factual ZIP-check wording). Pilot findings fixed before the batch: pages sharing an angle read alike (fixed with secondary angles and per-angle treat/occasion rotation); a school page emphasized anniversaries (occasions now follow the angle); Avalon received a workplace angle (special-logistics places now use the planning-first angle).

## 7. Production deployment (do not run without the owner)

1. Back up live (database + files) and save inquiries.
2. Deploy code: `cater-ice-cream-core` (CityStore change) and the `dev/` folder (tools + data file). No theme change.
3. On live (SSH, WP-CLI):
   ```
   wp eval-file dev/tools/content/city-inventory.php csv=~/city-inventory-before.csv
   wp eval-file dev/tools/content/city-content-20261116.php dry-run report=~/city-dry.json
   ```
   Check the summary: eligible count, data-file cities not eligible on live (listed as a warning), and any "kept" fields (live admin edits; proposals in the report).
4. Apply in batches with a backup folder outside the web root:
   ```
   mkdir -p ~/city-content-backups
   wp eval-file dev/tools/content/city-content-20261116.php backup=$HOME/city-content-backups limit=50 offset=0 report=~/city-1.json
   (repeat with offset=50, 100, 150, 200; an interrupted batch can simply be re-run)
   ```
5. `wp cic locations flush-cache`, then purge the SiteGround cache (`wp sg purge` or Site Tools → Speed → Caching → Flush). City pages are virtual routes, so there is nothing for `wp yoast index` to rebuild; the location sitemap is generated on request.
6. Check a few pages (`curl -sI`, view source): robots "index, follow", canonical = own URL; open `https://www.catericecream.com/cic-locations-sitemap.xml`. Confirm Settings → Reading "Discourage search engines" is off.

## 8. Rollback

- Content only: run the migration with each backup file, newest first:
  `wp eval-file dev/tools/content/city-content-20261116.php rollback=$HOME/city-content-backups/city-content-backup-<time>.jsonl`
  It deletes records the run created and restores previous field values, status and Reviewed flag for records it changed. Nothing else is touched.
- Full: restore the database backup from step 1 (this also loses inquiries received since, so it is the last resort).
- Local backups: `C:\laragon\backup\catericecream\pre-city-seo-20261116-112253\` (full DB) and `C:\laragon\backup\catericecream\city-content-runs\` (per-run JSONL).

## 9. Search Console follow-up

1. Sitemaps: confirm `sitemap_index.xml` is submitted; it lists `cic-locations-sitemap.xml` (no separate submission needed, but it can be added to watch its counts).
2. Pages report after 1–2 weeks: watch "Discovered/Crawled – currently not indexed" and "Duplicate without user-selected canonical" for city URLs.
3. URL Inspection on 5–10 representative cities (one per county, a shared-ZIP locality, an island/mountain page): Google-selected canonical = user canonical.
4. Performance: filter pages containing `/service-areas/california/`; compare impressions and clicks monthly.
5. Do not use the Indexing API for these pages. Never claim a page is indexed without Search Console evidence.
6. Revisit thin performers after 2–3 months: improve their copy, or (owner decision) set them to noindex in the city editor.
